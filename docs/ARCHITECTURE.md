# Architecture

Each device saves timer changes locally and the two converge by sync (see Watch). `TimerStore` validates, changes and atomically saves a timer action in one main-actor turn. It then schedules notifications and Live Activities through a serial, coalescing effects queue. Watch acknowledgements and UI interaction never wait for those system effects or notification permission dialogs. Core types depend only on Foundation. There is no backend or third-party runtime SDK.

## Timing and history

A running timer stores a deadline. Pauses close a running interval; resume opens a new one. Completion is reconciled against the deadline, including after relaunch. History snapshots preserve session names, colours and durations even when a preset changes or is deleted. Existing JSON without history remains readable. Updates keep the same on-device state path.

All timer surfaces use the same core action handler. Reset replaces the current attempt with a fresh, stopped session at its full configured duration. It does not reconcile or archive that attempt; existing saved history, including legacy reset records, stays intact. The old `restart` action is a reset-only compatibility alias. Only an explicit Start begins a new attempt. After a completion, `suggestedNext` offers a short break (a long break after every fourth focus that day) or, after a break, the most recent focus session; it is a button, never an automatic start. End still saves elapsed time, and switching to a different session saves the interrupted attempt. Pending completion alerts and Live Activities are cleared when resetting.

Stopwatch mode reuses the same session model. An untimed session counts its 12-hour limit down internally and shows the elapsed time, so pause, resume, end, reset, Watch commands, Live Activities and history need no second code path. Reaching the limit ends and saves the session rather than completing it, and that bound also keeps backups importable by older builds. A session's optional name (`title`) is set at Start and can be renamed while it runs. Mode is carried by the current session and only changes between sessions. Completion rates count timed sessions only. The new `untimed` and `title` fields are optional in saves, backups, Watch snapshots, commands and Live Activity state, so older data and companions still decode.

The state file is written atomically. The previous decodable save is kept beside it. A damaged primary file can fall back to that save. If both fail, the UI blocks writes instead of replacing history with an empty state. A previous save is a recovery aid, not a substitute for exporting backups.

Notifications and Live Activities are system-managed presentations. Neither guarantees app execution at the deadline. The app reconciles overdue sessions when it runs again. Focus/Silent Mode and notification permissions affect alerts.

## Export

The Markdown report contains finished sessions, UTC timestamps, active/planned seconds, pauses and outcomes. Names are opt-in. Time ranges select sessions by start date and include their complete active duration. JSON backups use a versioned schema with ISO-8601 dates. Import validates the schema and bounds, skips duplicate IDs and the current session ID, and never replaces preferences or an active timer. Import is additive, not full-device restore.

A share sheet is the only AI integration. The user picks the destination. This avoids credentials, a hosted MCP endpoint and background uploads. A future MCP service would require a separate authenticated bridge, explicit data scope and revocable access; none is exposed here.

## Watch

The Watch keeps its own `TimerState` and runs every action through the same `perform` path as the iPhone, so taps apply and save at once with no waiting, spinner or confirmation round trip. Each device stamps the current session with `changedAt` when it changes it; both reach the same value when a timer completes because the deadline is shared.

Sync uses one message type, `SyncEnvelope`, in both directions. The Watch sends its copy with `sendMessage` when the phone is reachable (the phone merges it and replies with its merged copy) and always also writes it to the application context, which the system delivers after a disconnection. The phone publishes the same way after every save and picks up the Watch's context when it launches. A send counts as delivered only after a reply, so a change made offline is sent again when the devices reconnect; a five-second silence or a send error marks the phone as away, which is the only time the Watch shows "Syncs with iPhone later".

`TimerState.merge` converges the two copies. History is a union by session ID, so a session completed or ended on both devices is saved once. The phone owns the presets. The newest change to the current session wins, with ties going to the phone. A session that either device has saved, or that the other deliberately discarded with Reset or a type change (`replacedIDs`), never becomes active again. If the other device's newer session wins while this device was still running a different one, that run is saved as switched instead of being lost. The Watch keeps finished sessions in a small outbox until the phone lists them in `finishedIDs`. The phone still runs notifications and Live Activities whenever it receives a change. iOS starts a Live Activity only while the app is in the foreground, so a session the Watch starts while the iPhone app is in the background gets one when the app next opens. The Watch app declares `WKSupportsLiveActivityLaunchAttributeTypes`, so tapping the mirrored Live Activity on the Watch opens the Watch app. Older Watch builds keep working through the previous `WatchSnapshot`/`WatchCommand` messages while both apps update.

The Watch widget (`WatchWidget`) shows the Watch app's current session. The app writes that session to an App Group (`group.` plus the bundle ID) whenever it changes or the app opens, and reloads the widget only then. The widget draws running time with `Text(timerInterval:)` from the stored dates, so countdowns and stopwatches stay live without frequent timeline reloads; a countdown also gets a second entry at its deadline. A WatchConnectivity background task lets the Watch app take in iPhone changes and refresh the widget while it is closed.

System delivery timing still depends on watchOS and iOS, and simulators do not establish physical Bluetooth or Wi-Fi latency.

## Mac

The Mac menu bar app is a separate, standalone writer. It saves its own `TimerState` with `StateFile` at `~/Library/Application Support/SimpleTimer/state.json` and changes it only through `perform`, but has no iPhone or Watch sync, history screen, export or settings window. `LSUIElement` keeps it out of the Dock. Until the drop-down opens, only the status item exists. The panel and its SwiftUI view are created on open and released on close. A one-second timer with tolerance redraws the menu bar only while a session runs. Timed sessions schedule one completion notification through `LatestEffectsQueue`; permission is asked after the first Start.

Menu bar managers (Ice, Thaw, Bartender) hide items by pushing them off screen, show them again in their own bar, and open one by revealing the real item and sending it a synthetic click or an accessibility press. Thaw 2 can follow its click with a second mouse up, and managers move items with ⌘-drags. So the item is a plain `NSStatusBarButton` with a target and action, sent on left and right mouse up. A second toggle within 0.3 seconds and ⌘-clicks are ignored. The item has a fixed `autosaveName` and accessibility identifier. The running time is drawn into its template image in monospaced digits, and the button title stays empty. Managers recognise items by their accessibility title, as [Thaw's developer guide](https://github.com/thaw-app/Thaw/blob/development/docs/APP_DEVELOPERS.md) explains, and the width stays the same from second to second. Only one copy runs: a second launch asks the first to show its drop-down, then quits. Opening the app from Finder or Spotlight shows the drop-down too, which reaches the timer when its icon is hidden.

The drop-down is a borderless, non-activating `NSPanel` at pop-up menu level, on all Spaces including full-screen ones. Ice and Thaw treat a window at that level as an open menu and keep the revealed item shown while it is open. The panel is placed once, on the screen under the pointer. It goes under the item if the item is visible on that screen and clear of the notch. Otherwise it goes under that screen's menu bar at the pointer: when a manager has hidden the item, the menu bar hides itself, or macOS 27 reports a mirrored item on another display. It is never attached to the item, so it doesn't move when a manager hides the item again. Its top edge stays fixed when its content grows. It closes on Esc, when it loses key status, or on a click elsewhere. It takes the keyboard without changing the frontmost app. Its accessibility subrole is a system dialog, not a standard window, so tiling window managers, which manage standard windows, leave it alone.

## Signing and publishing

The public project has no team ID, private bundle identifier, device ID or signing material. Developers supply an ignored local xcconfig. The initial public release is a clean snapshot, not the private development Git history. Simulator screenshots must use synthetic data. Never commit build directories, app containers, backups, signing files or local credentials.
